# Уведомления Telegram и серверный API

## Какие события отправляются

- Вопросы Совы PQ, баг-репорты и отзывы отправляются через `/api/admin-notification`; для FTP/PHP-хостинга есть fallback `/api/admin-notification.php`. Для этих трёх типов разрешены и гости, и вошедшие пользователи; гостевые обращения ограничены пятью за 10 минут на IP. Ограничение на Node serverless действует в рамках экземпляра функции, PHP-версия использует файл во временном каталоге сервера.
- Уведомление об оплате отправляет только `/api/yookassa-webhook` после повторной проверки платежа в YooKassa и сверки с серверным заказом. Браузер не может подделать событие оплаты через endpoint уведомлений.
- Endpoint возвращает успех только если Telegram API подтвердил доставку. Если Telegram недоступен или переменные не настроены, UI покажет ошибку вместо ложного подтверждения.
- Webhook записывает `telegramNotifiedAt` в заказ. При неудачной доставке он возвращает 503, чтобы провайдер мог повторить webhook; повторная обработка пытается доставить уведомление ещё раз.

## Обязательные переменные окружения

Задаются **на сервере**, не в Vite и не в клиентском коде:

- `PARMASTER_BOT_TOKEN` — новый токен бота, который присылает вопросы/отзывы/баг-репорты. Допускается имя `TELEGRAM_BOT_TOKEN`.
- `TELEGRAM_ADMIN_CHAT_ID` — Telegram chat ID получателя уведомлений. Бот должен быть запущен пользователем или добавлен в нужный чат/канал.
- `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY` — доступ к YooKassa.
- `FIREBASE_WEB_API_KEY`, `FIREBASE_SERVICE_ACCOUNT_JSON` — серверная проверка Firebase ID token и серверная запись платного доступа.
- `GEMINI_API_KEY` — необязательный ключ для расширенных ответов AI-помощника. Без него сайт использует локальную базу ответов, но ответы не будут генерироваться через Gemini.

Для отдельного сервиса автопубликации в соцсети используются `BATYA_BOT_TOKEN` или `TELEGRAM_PUBLISH_BOT_TOKEN`, `TELEGRAM_CHANNEL_ID`, `VK_ACCESS_TOKEN` и `VK_GROUP_ID`.

**Не добавляйте секреты в репозиторий, `VITE_*` переменные или сообщения чата.** Токены, которые раньше находились в исходниках, необходимо отозвать и заменить. Удаление из текущей ветки не удаляет их из Git history.

## Блокирующий вопрос инфраструктуры

В репозитории уже есть `vercel.json`, а Node serverless-функции лежат в `api/`. Но текущий GitHub Actions FTP workflow загружает только каталог `dist/`, поэтому сам по себе не разворачивает эти функции.

Самый прямой путь — создать Preview deployment этой ветки в Vercel, добавить туда серверные переменные, затем протестировать все события на preview-домене. Для production нужно отдельно решить, будет ли весь сайт переведён на Vercel или текущий FTP-хост настроят проксировать `/api/*` на Vercel. DNS/маршрутизацию не меняйте, пока preview и тестовая оплата не пройдут проверку. Не запускайте реальные платежи до подтверждения маршрутизации и end-to-end проверки.

## Проверка после настройки

1. В серверном окружении настроить переменные выше и задеплоить Node API.
2. Войти на сайт и отправить тестовый вопрос, баг-репорт и отзыв; убедиться, что каждое сообщение приходит в Telegram.
3. Удалить токен/чат ID из окружения на staging на короткое время и убедиться, что сайт показывает ошибку доставки, а не ложный успех.
4. В sandbox YooKassa оплатить тестовый заказ полной тестовой суммой, проверить выдачу доступа и одно уведомление в Telegram.
5. Проверить повторный webhook: доступ не должен выдаваться повторно, уведомление не должно дублироваться после успешной доставки.

## Важное для FTP-хостинга

В workflow стоит `dangerous-clean-slate: false`, поэтому FTP-деплой не удаляет автоматически старые файлы, которые удалили из Git. После ротации токенов администратору хостинга нужно вручную удалить старые файлы `api/create-payment.php`, `api/admin-notification.php` и `api/telegram-cron.php` из каталога сайта (предварительно сохранить резервную копию при необходимости). Не включайте `dangerous-clean-slate: true`: это может удалить другие файлы сайта.
